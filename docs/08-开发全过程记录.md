## 阶段 0 · 立项（11-02，车还没到）

### 起点：一台闲置的 iPhone + 一个"想动手"的念头

最初的诉求很模糊：想找一件"能把 AI 从屏幕里拽出来"的事。候选方案一路排除：

| 想法 | 结论 | 理由 |
|---|---|---|
| iPhone 折腾快捷指令 / NFC 贴纸 | ❌ | 上限低，本质还是软件自动化 |
| 越狱 / 逆向 iOS App | ❌ | iOS 18 无公开越狱；要逆就逆安卓版 APK，那 iPhone 只剩"用" |
| **OpenBot：手机当机器人大脑** | ✅ | 唯一能"造一个有身体的智能"的选项 |

### 第一个岔路口：买散件还是买整车

散件方案（TT 马达 + L298N + Arduino Nano + 底盘）看着"更像 DIY"，但报价 ¥150-200 还要自己焊接装配。

**转折点是一条查证**：OpenBot 的 **iOS App 只支持 BLE，不支持 USB 串口**。而 BLE 只有 ESP32 有，Arduino Nano 没有。也就是说，如果按中文教程买 Nano，**手机永远连不上车**。

→ 主控必须 ESP32；既然 ESP32 整车套件（¥83.69）已经焊好装好，散件方案整体作废。

### 第二个岔路口：电池体系

原计划 3 节 18650（11.1V）+ 降压模块。查了 MX1508 的规格：**上限约 9.6V**，3S 满电 12.6V 会烧。

→ 又收到卖家一条关键信息：**4 节 5 号电池，一路升压 6V 供电机，一路降压 3.3V 供 ESP32**。
→ 结论：18650、充电器、降压模块、电解电容**四样全部不买**，预算从 ¥300 降到 ¥185。

### 第三个岔路口：要不要立刻买编码器

卖家主动提醒"这底盘没码盘，需要自己做码盘实现里程计，或换带编码器的 TT 马达"。

盘了一遍目标：遥控、跟随、采数据训练——**全都不需要里程计**，OpenBot 的闭环靠摄像头。代价只是 App 里速度显示 0。
→ 决定：**第一阶段明确不做**，把 ¥80 留到"需要精确走 3 米"的那天。

### 这一阶段的产出

- 采购清单（整车 ¥83.69 + 镍氢 ¥65.7 + 手机夹 ¥25 + 杜邦线 ¥10）
- 《OpenBot 小车上手计划》HTML：四周节奏、验收标准、坑清单
- 一条重要认知：**商品页不可信，源码可信**

## 阶段 1 · 到货与刷机（11-04 傍晚）

### 18:24 · 拆箱

照片里已经是成品：ESP32 核心板、两块 MX1508、4 槽电池盒、四轮，全部焊装好。省掉了整个"焊接装配"环节。

**同时发现一处与详情页不符**：商品页写"2 后轮电机 + SG90 舵机转向"，实物是**四轮直驱差速**，没有舵机。这反而更简单——OpenBot 的 `DIY_ESP32` 原生就是差速。

### 18:30-18:37 · 环境

| 动作 | 结果 |
|---|---|
| 查串口 | `/dev/cu.usbserial-10`，CH340 **系统自带驱动**，不用装 |
| 读芯片 | ESP32-D0WD-V3 / 4MB / MAC `d4:d4:da:6c:48:7c` |
| 装 arduino-cli | `brew install` 被本机安全策略拦（写入阶段中断）→ 改用**官方二进制**下载到项目目录，成功 |
| 装 ESP32 核心 | `esp32:esp32@2.0.17`（对齐 OpenBot CI），约 1GB |
| clone 源码 | `github.com/ob-f/OpenBot`，浅克隆 |

### 18:40 · 从卖家固件里挖出引脚

卖家给的资料包里有一份 `.ino`，直接读到了全部关键信息：

| 项 | 值 |
|---|---|
| 左电机 | GPIO 19 / 21 |
| 右电机 | GPIO 32 / 33 |
| 停止语义 | 两脚同高 = 刹车 |
| **启动死区** | 占空比 < 75% 不转 |
| 电量检测 | 无 |
| 码盘 / 超声波 / LED | 无 |

### 18:44-18:47 · 改固件 + 首次编译

四处改动（详见 [05-固件适配说明](05-固件适配说明.md)）：

1. 电机引脚 → 19/21、32/33
2. **GPIO19 冲突**：OpenBot 默认把 19 当左前 LED，正好撞左电机 → LED 挪到 25/26
3. 分压/超声/码盘/LED/OLED 全关
4. `VOLTAGE_MIN/MAX = 4.5/6.0` → 对齐 75% 死区

编译结果：**1,128,017 字节，占 app 分区 86%**。

### 18:50 · 烧录（第一次失败）

`arduino-cli upload` 默认 921600 波特率 → `Failed to write to target Flash after seq`。
→ 改 esptool + **230400**，一次成功，Hash verified。

### 18:52 · 串口一片空白

以为固件没跑起来。查源码：`#define DEBUG 0`，压根不打印任何东西。
→ 改 `DEBUG 1` 重烧，日志正常。

### 18:54 · BLE 验证通过

macOS 上用命令行扫 BLE 拿不到 CoreBluetooth 权限（无头进程），换 iPhone 装 **nRF Connect**：扫到 **`OpenBotCar`**，服务 UUID `61653DC3-…-8B4EEC61D613`，广播间隔 40ms。

→ **软件链路全部验证完毕**：固件编译 ✅ 烧录 ✅ 开机自启 ✅ BLE 广播 ✅。只剩"电机通电"等电池。

### 顺带完成 · 原厂固件备份

`read-flash 0 0x400000`，460800 失败 → 230400，耗时 **3 分 12 秒**，4MB 完整镜像。

### 18:57-19:02 · 让过程可见

用户的反馈很直接：*"控制界面和你写的代码我都看不到，都是你后台干的事。"*

→ 做了两样东西：

- `scripts/ob.sh`：`status / build / flash / monitor / backup / restore / pinmap`，用户自己能跑、自己能看到输出
- `web/OpenBot项目控制台.html`：一页看全硬件核对结果、引脚表、带时间戳的操作流水、固件改动、文件路径

**这条反馈改变了后续的协作方式**：每完成一步，贴关键输出原文，而不是只说结论。

### 19:05 · 把"测试"前置

用户的疑问：*"装电池就得拔数据线，但烧录又要插线，这冲突吗？"*

答案是"换班不冲突"（烧录关电池开关，跑车拔 USB），但这个问题暴露了一个更好的方案：
**方向测试根本不需要控制端**。

→ 写了 `firmware/moto-test/`：通电后自动循环"左轮正/反 → 右轮正/反 → 全部正/反"，串口同步打印步骤名。
→ 在电池未到、USB 供电的安全状态下**提前烧好**。
→ 电池到货流程从 5 步压缩到 3 步，且全程不碰电脑。

## 三条方法论（比技术结论更可复用）

1. **先查"连接方式"，再买硬件**
   这一个检查（iOS 只支持 BLE）救了整份采购清单。硬件项目里，通信链路决定了 80% 的选型。

2. **文档与实物冲突时，信源码**
   舵机 vs 差速、VCC 接 3.3V 的疑云、"电池电压大于 9V"的模板文案——三次都是商品页不可信，源码/实测可信。

3. **把"必须连电脑"的步骤前移到"没电池"的时候**
   方向测试本该在装电池后做（那时不能插 USB），但因为它是独立固件，可以提前烧进去，把两条约束解耦。**约束冲突时，先想能不能改顺序，而不是硬碰。**
