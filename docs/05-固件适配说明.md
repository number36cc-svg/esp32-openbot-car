# 05 · 固件适配说明（改了哪 4 处、为什么）

> 基线：OpenBot 官方 `firmware/openbot/openbot.ino`（MIT，Intel ISL）。
> 本仓库的 `firmware/openbot/openbot.ino` 是**唯一改动版**，下面每一处改动都能在文件里搜到对应注释。

---

## 改动一览

| # | 改什么 | 原值 | 新值 | 不改会怎样 |
|---|---|---|---|---|
| 1 | 电机引脚 | L: 32/33, R: 25/26 | **L: 19/21, R: 32/33** | 电机不动/乱转 |
| 2 | LED 引脚（避免冲突） | `PIN_LED_LF = 19` `PIN_LED_RF = 12` | **25 / 26** | LED 代码与左电机抢 GPIO19 |
| 3 | 外设开关 | 分压/超声/码盘/LED 多为 1 | **全部 0** | 读浮空引脚、干扰电机 |
| 4 | 电池与控制死区 | 9.0/12.6 | **4.4 / 6.0 / 4.5** | 摇杆推一半不动、推到底猛窜 |

外加：`BLE_NAME "OpenBotCar"`、`DEBUG 1`（方便调试）。

## 1. 电机引脚

```c
// 原
const int PIN_PWM_LF1 = 32;   const int PIN_PWM_LF2 = 33;
const int PIN_PWM_LB1 = 32;   const int PIN_PWM_LB2 = 33;
const int PIN_PWM_RF1 = 25;   const int PIN_PWM_RF2 = 26;
const int PIN_PWM_RB1 = 25;   const int PIN_PWM_RB2 = 26;

// 改后（左 19/21，右 32/33，前后并联）
const int PIN_PWM_LF1 = 19;   const int PIN_PWM_LF2 = 21;
const int PIN_PWM_LB1 = 19;   const int PIN_PWM_LB2 = 21;
const int PIN_PWM_RF1 = 32;   const int PIN_PWM_RF2 = 33;
const int PIN_PWM_RB1 = 32;   const int PIN_PWM_RB2 = 33;
```

**为什么前后用同一组引脚**：本车左右两侧各有 2 个马达**并联**接在同一组 MX1508 输出上，物理上就是同一个通道。固件里把"左前/左后"都指到 19/21，"右前/右后"都指到 32/33，即可复用 OpenBot 的"左右轮速度"抽象，不用改任何驱动逻辑。

**不用改控制协议的原因**：OpenBot 的电机函数是"每侧两脚，一个置高一个给 PWM，停止时两个都置高"——正好等于 MX1508 的刹车语义（两脚同高 = 短路制动）。

## 2. ⚠️ LED 引脚冲突（最容易漏的坑）

```c
// 原：GPIO19 被左前 LED 占用，正好是本车左电机 IN1
const int PIN_LED_LF = 19;
const int PIN_LED_RF = 12;

// 改后：挪到没人用的 25 / 26（本车没有 LED，这里只是防止代码抢脚）
const int PIN_LED_LF = 25;
const int PIN_LED_RF = 26;   // 注意：原为 19，与左电机冲突，已改
```

**为什么必须改**：`digitalWrite(PIN_LED_LF, ...)` 和 `ledcWrite(左电机通道, ...)` 会打同一个 GPIO。表现为"电机偶发抽动""一按遥控就抖"——这种 bug 极难定位，因为它取决于 LED 逻辑的调用时机。

**通用规则**：移植固件时，把新引脚号丢进原文件里全局搜一遍，确认没有第二处引用。

## 3. 外设开关全关

```c
#define HAS_VOLTAGE_DIVIDER 0    // 板上没有分压电阻 → 关，否则读到浮空值
#define HAS_INDICATORS 0
#define HAS_SONAR 0              // 没有超声波
#define SONAR_MEDIAN 0
#define HAS_BUMPER 0
#define HAS_SPEED_SENSORS_FRONT 0 // 没有码盘
#define HAS_SPEED_SENSORS_BACK 0
#define HAS_SPEED_SENSORS_MIDDLE 0
#define HAS_LEDS_FRONT 0
#define HAS_LEDS_BACK 0
#define HAS_LEDS_STATUS 0
#define HAS_OLED 0
#define HAS_BLUETOOTH 1           // ← 唯一的 1
#define BLE_NAME "OpenBotCar"
```

**代价**（可以接受）：

- App 里**速度显示恒为 0**（没有编码器，没得测）
- App 里**电量显示为空**（没有分压采样，不知道电池电压）

**原则**：移植时**默认全关，逐个打开**。反过来的话，浮空引脚上的随机电平会被当成"传感器数据"，轻则显示乱跳，重则干扰相邻输出。

## 4. 电池参数与 75% 启动死区

```c
// 4 × AA 镍氢：满电约 5.6-6.0V，空电约 4.4V
// VOLTAGE_MIN/VOLTAGE_MAX 决定固件的最小控制量 ctrl_min = 255 * MIN / MAX
// 卖家固件要求占空比 >= 75% 电机才转 -> 4.5/6.0 = 0.75 -> ctrl_min ≈ 191
#define VOLTAGE_LOW 4.4f
#define VOLTAGE_MAX 6.0f
#define VOLTAGE_MIN 4.5f
```

**这是本项目最"巧"的一处**：OpenBot 把用户速度换算成电压再换算成占空比，而 `ctrl_min = 255 × VOLTAGE_MIN / VOLTAGE_MAX`。把 `VOLTAGE_MIN` 设成 `0.75 × VOLTAGE_MAX`，等于告诉固件"低于 191 的控制值等同于 0"——**摇杆一推就起步，不会出现"前 3/4 行程无反应"的死区手感**。

```
未补偿：  摇杆 0%──────────────75%│▏100%   ← 前 3/4 全是死区
已补偿：  摇杆 0%│▏────────────100%      ← 全行程有效
```

> 换车标定方法：手动写个小程序，从 0 慢慢加占空比，记下电机**刚好开始转**的百分比 P，然后
> `VOLTAGE_MIN = P × VOLTAGE_MAX`。

## 5. 方向自动测试固件（`firmware/moto-test/`）

用途：**电池装好后，不需要手机、电脑、App、手柄，通电就能测四轮方向。**

行为：循环执行 6 步，每步 2 秒 + 停 1 秒 + 滑行 0.7 秒

```
[1] 左轮 正转   [2] 左轮 反转
[3] 右轮 正转   [4] 右轮 反转
[5] 全部 正转   [6] 全部 反转
```

串口（115200）同步打印每一步的名字，判断标准：**"正转"时轮子应朝车头方向滚**。

⚠️ 两个注意：

1. **这个固件不初始化 BLE**，所以 nRF Connect 扫不到 `OpenBotCar` 是正常的
2. **通电瞬间电机就会动**，务必先把车架空（垫起来让四轮悬空）

测完方向、改好引脚后，重新烧 `firmware/openbot` 即可。

## 6. 换一台车怎么改（移植步骤）

1. 拿到卖家源码或接线图，**抄出四件事**：左侧 IN1/IN2、右侧 IN1/IN2、驱动芯片型号、供电方式
2. 改 `PIN_PWM_L*` / `PIN_PWM_R*` 四组（前后四对）
3. 全局搜索这些 GPIO，确认没有别的功能占用（尤其 LED / I2C / 串口）
4. 外设开关全设 0，`HAS_BLUETOOTH 1`
5. 按电池实际电压填 `VOLTAGE_LOW / MAX`，按实测起转占空比填 `VOLTAGE_MIN`
6. 编译看占用率（>95% 就要考虑砍功能）
7. 先烧 `moto-test` 验证方向，再烧正式固件
