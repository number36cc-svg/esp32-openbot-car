# 10 · 代码与通信原理详解

> 这篇回答三个问题：**手机/电脑怎么连上小车的？指令是怎么让轮子转起来的？每一层代码在干什么？**
> 读完后你应该能自己画出一整条控制链路。

---

## 一、全景：一条控制指令的旅程

```
你的手指（浏览器摇杆 / 键盘 / 终端按键）
    │
    ▼
┌─────────────────────────────────────────────┐
│ Mac / iPhone 上的"遥控器"                     │
│  · webdrive.py   浏览器遥控（推荐）            │
│  · drive.py      终端遥控（单键）              │
└──────────────┬──────────────────────────────┘
               │ ① WebSocket（浏览器↔服务器，本机内）
               │ ② BLE 无线（Mac↔小车，约 20 次/秒）
               ▼
┌─────────────────────────────────────────────┐
│ 小车上的 ESP32（固件 openbot.ino）             │
│  收字节 → 解析 → 算左右轮 → 生成 PWM            │
└──────────────┬──────────────────────────────┘
               │ ③ 电信号（GPIO 引脚）
               ▼
┌─────────────────────────────────────────────┐
│ MX1508 驱动芯片 ×2 → 4 个 TT 电机              │
│  小电流指令 → 大电流动力                       │
└─────────────────────────────────────────────┘
```

三个关键角色各司其职：

| 角色 | 谁来干 | 干什么 |
|---|---|---|
| **遥控器** | Mac 跑的 Python + 浏览器页面 | 把人的意图（按键/摇杆）翻译成"左轮 x、右轮 y"两个数字 |
| **大脑** | ESP32 固件 | 收两个数字，变成 4 路精确的电压脉冲（PWM） |
| **肌肉** | MX1508 + 电机 | 把小信号放大成能转轮子的电流 |

## 二、无线连接：BLE 是怎么建立的

### 2.1 BLE 的"广播—发现—连接"模型

BLE（低功耗蓝牙）和耳机的传统蓝牙不是一回事：

```
小车（ESP32）                          Mac / iPhone
   │                                      │
   │ ①不断喊："我叫 OpenBotCar，           │
   │   我的服务是 61653dc3-..."            │
   │  （广播，每 40ms 一次）               │
   │ ◄──────────── 扫描 ─────────────────│ ②遥控脚本扫描，
   │                                      │   按名字找到它
   │ ◄──────────── 连接请求 ─────────────│ ③发起连接
   │                                      │
   │ ══════════ 连接建立（双向）══════════ │
```

- **固件侧**（`openbot.ino` 660-735 行附近）：ESP32 上电后用 `BLEDevice` 库创建一个"服务器"，开始广播。它声明了三个 UUID：

| UUID | 角色 | 方向 |
|---|---|---|
| `61653dc3-...` | Service（服务） | 身份标识 |
| `06386c14-...` | RX 特征值 | **Mac → 小车** 写指令 |
| `9bf1103b-...` | TX 特征值 | 小车 → Mac 发日志/状态 |

- **遥控脚本侧**（`drive.py` / `webdrive.py`）：用 `bleak` 库扫描，找到 `name == "OpenBotCar"` 的设备，连上后拿到两个"特征值"的句柄。

### 2.2 为什么手机设置里看不到它

iOS/Android 的蓝牙设置列表只显示**需要配对的传统蓝牙设备**。BLE 自定义设备必须由 App 主动扫描才能发现——这是所有手环、体脂秤都要装 App 的原因，不是 bug。

### 2.3 验证连接的工具

装个 **nRF Connect**（手机免费 App），能扫到 `OpenBotCar`、看到它的 UUID、甚至手动连上——调 BLE 问题时它是"X 光机"。

## 三、协议：指令长什么样

### 3.1 帧格式（纯文本，人能直接读）

遥控器往 RX 特征值写入一串字节，以 `\n` 结尾：

```
c:130,130\n     ← 控制：左轮 130，右轮 130（范围 -255..255）
h400\n          ← 心跳："我还活着"，400ms 超时
```

- **正数 = 前进，负数 = 后退，0 = 停**
- 左右不同 = 差速转弯（左 51 右 170 = 画左弧线；左 200 右 -200 = 原地左转）

> ⚠️ 历史坑：心跳曾经写成 `h:400`，固件用 `atol()` 解析时把冒号带进去算出 **0**，
> 导致"永远超时 → 指令刚到就被清零 → 电机只嗡不转"（坑 23）。
> 现在统一发 `h400`，固件也做了兼容。

### 3.2 心跳保命机制

```
遥控器：每 50ms 发一次 c:...，同时发 h400
固件：  收到 h 就刷新计时器
        如果 400ms 没收到任何 h → 主动把两轮清零（车自动停）
```

这是**安全设计**：Mac 蓝牙抽风、脚本崩溃、人走出范围……无论哪种失联，车都会自己停住，不会带着最后一条"前进"指令狂奔。

## 四、固件侧：两个数字怎么变成轮子转动

### 4.1 消息解析流水线（openbot.ino）

```
BLE 收到字符 ──► on_ble_rx()
                  ├─ 第 1 个字符是 header（'c' / 'h' / ...）→ 存起来
                  ├─ 后续字符 → 追加进 msg_buf
                  └─ 遇到 '\n' → parse_msg()
                                  ├─ header='c' → process_ctrl_msg()
                                  │     strtok 按 ",:" 切开 → ctrl_left / ctrl_right
                                  └─ header='h' → process_heartbeat_msg()
                                        记录间隔 + 刷新计时器
```

每个主循环（几十次/秒）都会执行：

```
ctrl_left, ctrl_right
   │  ① 心跳检查：超时 → 清零（安全停）
   │  ② 限幅：钳到 [-255, 255]
   ▼
update_vehicle() → update_left_motors() / update_right_motors()
   │
   │  ctrl_left > 0  → 引脚 19 输出 0，引脚 21 输出 PWM   （正转）
   │  ctrl_left < 0  → 引脚 19 输出 PWM，引脚 21 输出 0   （反转）
   │  ctrl_left = 0  → 两脚都输出 255                     （刹车：双高）
   ▼
ledcWrite(通道, duty)   ← ESP32 硬件 PWM，8 位分辨率（0..255）
```

注意 ESP32 上 `analogWrite` 是被宏替换成 `ledcWrite` 的——**参数是 LEDC 通道号不是引脚号**，固件在 setup 阶段就把 GPIO19/21 绑到通道 0/1、GPIO32/33 绑到通道 2/3（`ledcAttachPin`），这是这套代码最绕的一处。

### 4.2 死区映射：duty_from_ctrl()（本项目原创改动）

这辆车的物理特性：**占空比低于 75%（约 191/255）电机根本不转**（齿轮静摩擦 + MX1508 压降）。如果不处理，摇杆前 3/4 行程都是死的。

```c
int duty_from_ctrl(int ctrl) {
  int mag = abs(ctrl);                                   // 0..255
  int duty = MOTOR_MIN_DUTY + (255 - MOTOR_MIN_DUTY) * mag / 255;
  return constrain(duty, MOTOR_MIN_DUTY, 255);           // 191..255
}
```

效果：

```
控制量   0 ──── 1 ──────────────── 255
实际占空比 停   191(刚好转) ──────── 255(全速)
```

推一点点车就动，推到底全速，中间 64 级用来画弧线。
**为什么不做在"最小控制量"上**：OpenBot 原生有个 `ctrl_min` 限幅，把死区塞进去会剩
`ctrl_max - ctrl_min = 1` 个台阶——摇杆变开关，车只会直冲不会转弯（坑 21）。
**限幅防误触发，输出端映射才治物理死区**，两类问题长得像，解法相反。

### 4.3 电气层：MX1508 怎么"听懂" PWM

```
GPIO19 (PWM 0 或 duty)  ──► MX1508 #1 ──► 电机 A（左侧前后并联）
GPIO21 (PWM 0 或 duty)  ──┘

两脚一高一低 = 正/反转；两脚同高 = 刹车（短路制动）；两脚同低 = 滑行
MX1508 内部是 4 个 MOS 管 H 桥：小信号控制电池大电流的方向和"通电时间占比"
```

占空比 87% 的意思是：每秒内电机有 87% 时间接电池、13% 断开——转得比 100% 慢一点，肉眼看就是变速。

## 五、遥控器侧：人的意图怎么变成两个数字

### 5.1 drive.py（终端版）的局限

- 用 `termios` 把终端调成 cbreak 模式逐键读取
- 每个按键记录"最后按下时间"，0.5 秒内算"仍按住"（TTL 机制，因为**终端没有松键事件**）
- macOS 只给最后按下的键发重复信号 → **W 和 A 无法持续同时按住**（只能短暂组合）——这是终端先天限制，无解，所以才做了 webdrive

### 5.2 webdrive.py（浏览器版）的架构

```
浏览器页面（摇杆 + W/A/S/D）
    │ WebSocket（json: {"t":"keys","keys":["w","a"]}）
    ▼
aiohttp 服务器（跑在 Mac 上，端口 8765）
    │ 更新全局 InputState
    ▼
BLE 写入循环（20Hz）
    │ control() 把按键/摇杆状态算成 (左, 右)
    ▼
小车
```

**为什么浏览器能解决"同时响应"**：浏览器键盘有真正的 `keydown`/`keyup` 事件，
W 和 A 可以各自独立地"按下/松开"，按住状态是真实存在的，不靠猜。

**摇杆为什么更细腻**：摇杆给出的是连续坐标 `(x, y)`（-1..1），控制量按
`左 = y + x，右 = y - x` 混合——这是标准的**差速混控公式**，斜推 45° 就是完美弧线；
键盘只有 8 个离散方向。

页面本身是一段内嵌在 Python 里的 HTML（零依赖），手机 Safari 打开同一个地址就能用——
**这也是"不编译 iOS App 就能用手机遥控"的过渡方案**。

### 5.3 控制值对照表

| 输入 | 左轮 | 右轮 | 效果 |
|---|---|---|---|
| W（键盘） | 170 | 170 | 直行（中速） |
| W+A | 51 | 170 | 左弧线 |
| A | -200 | 200 | 原地左转 |
| 摇杆正前 | 255 | 255 | 直行（全速） |
| 摇杆左上 45° | 85 | 255 | 大半径左弧 |
| 松手/空格/Q | 0 | 0 | 刹车 |

## 六、把代码跑起来的三种方式

```bash
# ① 终端遥控（最快，但只能单键）
./remote-control/run-drive.sh

# ② 浏览器遥控（推荐：组合键 + 摇杆 + 手机可用）
./remote-control/run-webdrive.sh
#   Mac 开 http://localhost:8765 ，iPhone 同 WiFi 开 http://<Mac的IP>:8765

# ③ 改固件 → 编译 → 烧录（改车行为时才需要；烧录时必须关电池开关）
./scripts/build.sh
esptool --port /dev/cu.usbserial-10 --baud 230400 write-flash \
  --flash-mode dio --flash-freq 40m --flash-size 4MB \
  0x1000 firmware/build/openbot.ino.bootloader.bin \
  0x8000 firmware/build/openbot.ino.partitions.bin \
  0x10000 firmware/build/openbot.ino.bin
```

依赖安装：`remote-control/.venv` 里有 bleak（BLE）+ aiohttp（Web），
重建方法见 [03-刷机指南](03-刷机指南.md)。

## 七、常见排查顺序（背下来）

```
车不动？
├─ 终端/页面有反应吗？没有 → 蓝牙没连上：nRF Connect 扫 OpenBotCar
│                            扫不到 → 车没电 / 电源开关没开 / 跑的还是测试固件
├─ 有反应但电机只嗡不转？ → 心跳 bug（坑23，已修）或电池亏电
├─ 轮子转但方向反了？     → 固件里对调 GPIO19/21（或 32/33）重烧
└─ 能动但抖一下就停？     → 电池电压拉垮（4节镍氢亏电），充电
```
